# SPFx Migration Banner

A SharePoint Framework (SPFx) Application Customizer that displays a configurable migration notice on modern SharePoint Online sites.

The banner can provide:

- A configurable title and message
- A destination SharePoint site URL
- A retirement date
- An optional migration FAQ link
- A primary **Go to New Site** action
- A secondary **Migration FAQ** action

The solution is designed for tenant-to-tenant Microsoft 365 migrations. Deploy the package tenant-wide, then activate and configure the banner only on selected sites through site-scoped SharePoint custom actions.

> This project targets modern SharePoint Online pages and uses the supported SPFx `PlaceholderName.Top` placeholder. Classic SharePoint pages require a separate fallback approach.

## Solution overview

The recommended deployment model is:

```text
Tenant-wide SPFx package
          +
Site-scoped custom action
          +
Site-specific banner properties
```

The package is available throughout the tenant, but the extension exits without rendering when `targetSiteUrl` is not supplied. A PnP PowerShell custom action activates and configures the banner only on a migration site.

### SPFx component ID

```text
7a33743b-bd78-4e40-9d1d-5b84f99b8b5f
```

The custom-action instance ID generated by SharePoint will be different. Always use the component ID above for `ClientSideComponentId`.

## For administrators: deploy and configure

> [!TIP]
> You can view a specific package deployment and application example here -> [Package Deployment and Activation Example](dev_notes/Package_Deployment_and_Activation_Example.md)

### 1. Upload the package to the tenant App Catalog

1. Open the tenant App Catalog.
2. Open **Apps for SharePoint**.
3. Upload:

   ```text
   sp-fx-migration-banner.sppkg
   ```

4. Select **Make this solution available to all sites in the organization**.
5. Deploy the solution.

#### Important tenant-wide behavior

Tenant-wide deployment makes the Application Customizer available across the tenant. This project is intended to render nothing when `targetSiteUrl` is absent.

Do not configure a default target URL in the tenant-wide extension instance. Site-specific custom actions should supply the migration settings.

If an older build still contains fallback behavior that displays a default banner without `targetSiteUrl`, update the code before tenant-wide deployment:

```typescript
const targetSiteUrl = this.properties.targetSiteUrl;

if (!targetSiteUrl) {
  return;
}
```

### 2. Install PnP PowerShell

Run from PowerShell 7:

```powershell
Install-Module PnP.PowerShell -Scope CurrentUser
```

If PnP PowerShell is already installed, update it according to the organization's normal change-control process.

### 3. Connect to the target site

```powershell
$siteUrl = 'https://sourceTenant.sharepoint.com/sites/TechInsiders'

Connect-PnPOnline `
    -Url $siteUrl `
    -Interactive
```

Use the authentication method approved for the tenant. Some environments require an Entra ID application/client ID for PnP PowerShell authentication.

### 4. Define the banner configuration

Use a PowerShell object and `ConvertTo-Json` instead of manually composing JSON. This avoids malformed quotes and line breaks.

```powershell
$bannerProperties = [ordered]@{
    bannerTitle   = '⚠ MIGRATION NOTICE'
    bannerMessage = 'This site has moved to the new Microsoft 365 tenant. Please use the new location going forward.'
    targetSiteUrl = 'https://targetTenant.sharepoint.com/sites/TechInsiders'
    retirementDate = '31 December 2026'
    faqUrl         = 'https://targetTenant.sharepoint.com/sites/MigrationFAQ'
}

$bannerPropertiesJson = $bannerProperties | ConvertTo-Json -Compress
```

The `faqUrl` and `retirementDate` values may be empty when they are not required:

```powershell
$bannerProperties = [ordered]@{
    bannerTitle    = '⚠ MIGRATION NOTICE'
    bannerMessage  = 'This site has moved. Please use the new location going forward.'
    targetSiteUrl  = 'https://targetTenant.sharepoint.com/sites/TechInsiders'
    retirementDate = ''
    faqUrl          = ''
}
```

### 5. Remove an existing migration-banner custom action

Run this before creating or replacing the configuration to prevent duplicate site-scoped instances:

```powershell
Get-PnPCustomAction -Scope Web |
    Where-Object { $_.Name -eq 'MigrationBanner' } |
    ForEach-Object {
        Remove-PnPCustomAction `
            -Identity $_.Id `
            -Scope Web `
            -Force
    }
```

This removes only the web-scoped custom action named `MigrationBanner`.

### 6. Add the configured custom action

```powershell
Add-PnPCustomAction `
    -Name 'MigrationBanner' `
    -Title 'MigrationBanner' `
    -Location 'ClientSideExtension.ApplicationCustomizer' `
    -ClientSideComponentId '7a33743b-bd78-4e40-9d1d-5b84f99b8b5f' `
    -ClientSideComponentProperties $bannerPropertiesJson `
    -Scope Web
```

`Web` scope applies the configuration to the connected SharePoint web. This is recommended for migration scenarios because each site can have a different target URL, retirement date, and FAQ URL.

### 7. Verify the custom action

```powershell
Get-PnPCustomAction -Scope Web |
    Where-Object { $_.Name -eq 'MigrationBanner' } |
    Select-Object Name,
                  Location,
                  Scope,
                  ClientSideComponentId,
                  ClientSideComponentProperties |
    Format-List
```

Verify that:

- `Location` is `ClientSideExtension.ApplicationCustomizer`
- `Scope` is `Web`
- `ClientSideComponentId` is `7a33743b-bd78-4e40-9d1d-5b84f99b8b5f`
- `ClientSideComponentProperties` contains valid JSON

### 8. Test the deployed banner

1. Stop any local development server.
2. Open the target site using its normal URL.
3. Do not include `debugManifestsFile`, `loadSPFX`, or `customActions` query parameters.
4. Confirm the banner is displayed once.
5. Test both links.
6. Test a site without a `MigrationBanner` custom action and confirm that no banner is displayed.

## Update an existing site's configuration

The simplest controlled update is to remove and recreate the custom action:

```powershell
Get-PnPCustomAction -Scope Web |
    Where-Object { $_.Name -eq 'MigrationBanner' } |
    ForEach-Object {
        Remove-PnPCustomAction `
            -Identity $_.Id `
            -Scope Web `
            -Force
    }

Add-PnPCustomAction `
    -Name 'MigrationBanner' `
    -Title 'MigrationBanner' `
    -Location 'ClientSideExtension.ApplicationCustomizer' `
    -ClientSideComponentId '7a33743b-bd78-4e40-9d1d-5b84f99b8b5f' `
    -ClientSideComponentProperties $bannerPropertiesJson `
    -Scope Web
```

## Remove the banner from a site

```powershell
Get-PnPCustomAction -Scope Web |
    Where-Object { $_.Name -eq 'MigrationBanner' } |
    ForEach-Object {
        Remove-PnPCustomAction `
            -Identity $_.Id `
            -Scope Web `
            -Force
    }
```

Removing the site custom action disables the configured banner on that site. It does not remove the tenant-wide package.

## Configuration properties

### `bannerTitle`

Title displayed at the top of the banner.

Example:

```text
⚠ MIGRATION NOTICE
```

If omitted on a configured site, the code may use its built-in title fallback.

### `bannerMessage`

Primary explanatory message.

Example:

```text
This site has moved to the new Microsoft 365 tenant. Please use the new location going forward.
```

### `targetSiteUrl`

Destination URL for **Go to New Site**.

This property is required to render the banner. When it is absent or empty, the extension exits without displaying anything.

### `retirementDate`

Optional display value appended to the retirement message.

Example:

```text
31 December 2026
```

The value is currently treated as display text rather than parsed as a date.

### `faqUrl`

Optional URL for the **Migration FAQ** button. When it is absent or empty, the FAQ button is not displayed.

## Troubleshooting

### No banner appears after deployment

Check the following:

1. The package is deployed in the tenant App Catalog.
2. The `.sppkg` file reflects the latest `npm run build`.
3. The site has a web-scoped `MigrationBanner` custom action.
4. The custom action uses the correct component ID.
5. `targetSiteUrl` exists and is not empty.
6. `ClientSideComponentProperties` contains valid JSON.
7. The production test URL contains no localhost debug parameters.

Inspect the custom action:

```powershell
Get-PnPCustomAction -Scope Web |
    Where-Object { $_.Name -eq 'MigrationBanner' } |
    Format-List *
```

### Two banners appear

This normally means two extension instances are rendering, such as:

- A tenant-wide or feature-activated default instance
- A manually added site-scoped custom action

Confirm that the tenant-wide/default instance exits when `targetSiteUrl` is absent. Then ensure there is only one web-scoped `MigrationBanner` custom action.

### Local manifest cannot be loaded

Open the exact manifest URL emitted by `npm start` in the same browser.

On Windows, verify the listener:

```powershell
netstat -ano | findstr 4321
```

On Linux:

```bash
ss -ltnp | grep 4321
```

Check the development certificate, local firewall, browser trust, proxy, and endpoint security configuration.

### `Local gulp not found`

This is a Heft-based SPFx 1.23 project. Use:

```bash
npm run build
npm start
```

Do not install a local Gulp dependency merely to run commands from an older SPFx toolchain.

## Global Heft and local Heft report different behavior

Remove dependence on the global executable. Use the repository's npm scripts or `npx heft`, both of which resolve the project-local dependency.

## Security and operational notes

- Do not store credentials, client secrets, access tokens, or certificates in custom-action properties.
- Validate destination and FAQ URLs before rollout.
- Use HTTPS URLs.
- Treat the retirement date as user-facing display text and apply a consistent organizational format.
- Test the banner in modern pages, document libraries, lists, and supported browsers.
- Test responsive behavior at narrow browser widths.
- Maintain a migration inventory that maps each source site to its destination URL and configuration.
- Remove the site-scoped custom action when the legacy site is retired or the notice is no longer required.
- Classic SharePoint pages are outside the primary scope of this SPFx placeholder implementation.

## Build-tooling note

SPFx 1.23 uses the Heft-based toolchain for newly generated projects. The project's committed `package.json` and lock file should remain the source of truth for build-tool versions. Avoid introducing global dependencies into the required developer workflow when the repository already includes the same tool as a local development dependency.
